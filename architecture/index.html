Architecture

This page is for people who want to change venv-patcher. It shows how the code is built and why.

Goals

  • Plain git underneath. A patched package is a normal git repository. You can look at it with normal git commands.

  • Repeatable. The same input gives the same commits. Names and dates are pinned.

  • Record everything. Each result goes to the manifest right away, also a failure.

  • No surprises. A changed patch is never applied on top of the old one.

How a command runs

        flowchart TD
    A[cli.py: main<br/>parse argv] --> B[core.py: ensure_running_in_venv]
    B --> C{command}
    C -- apply --> D[cli.py: cmd_apply]
    C -- list --> E[cli.py: cmd_list]
    C -- reset --> F[cli.py: cmd_reset]
    D --> G[core.py: load_patch_entries<br/>YAML or TOML]
    D --> H[core.py: resolve_package_dir<br/>ensure_git_initialized<br/>apply_patch_file]
    F --> I[core.py: reset_package]
    D & E & F --> M[manifest.py<br/>load / save]
    H & I --> J[(git)]

  1. cli.main parses the command line with argparse. Then it checks that it runs in a venv.

  2. Each command has one cmd_<name> function in cli.py.

  3. cmd_apply reads each patches file and handles each entry in _apply_one.

  4. core.py does the work on disk: import, git, hashes, file parsing.

  5. manifest.py loads and saves the manifest.

Key decisions

git, not a copy

venv-patcher could keep a copy of each package. It uses git instead:

  • reset is one git reset --hard.

  • You can look at what changed with git log and git diff.

  • git am and git apply already handle patches well.

Pinned identity

Commits get a fixed name, email and date. The fallback date is 1970. So the initial commit only depends on the package files. This makes problems easy to compare between machines.

git runs without maintenance

venv-patcher runs git many times in a row, in folders it does not own. It turns off gc.auto and maintenance.auto for each call, with GIT_CONFIG_COUNT. Otherwise git may start work in the background, and leave lock files behind.

The manifest lives in the venv

The manifest is in site-packages. So each venv has its own, and you never pass a path to list or reset. Deleting the venv removes everything.

Save after each step

apply saves the manifest after each change. If a later step fails, or the process is stopped, the manifest still says what happened.

TOML only on Python 3.11 or newer

tomllib is part of Python since 3.11. venv-patcher still supports 3.9. So it reads TOML only when tomllib is there. On older Pythons a .toml file stops with a clear error.

Notice changes from pip

venv-patcher commits every change it makes. So git status shows any change someone else made, for example pip during an upgrade. Then apply stops, and reset keeps the files and drops the history. A hard reset there would put back the files of the old version.

Functions of the right size

complexipy limits each function to a complexity of 8. Within that limit, a function keeps its steps together. A small helper with only one caller is merged back into that caller. A helper stays when it is used more than once, or when merging it would go over the limit.
